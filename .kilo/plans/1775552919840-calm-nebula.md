# Livestream Refactoring Plan: Provider-Agnostic Architecture

## Current State Analysis

After reviewing the codebase, here's what I found:

### Current Architecture
1. **LivestreamController** (`lib/src/livestream/livestream_controller.dart`)
   - Central orchestrator that manages the livestream lifecycle
   - Connects to both `MediaService` (LiveKit) and `SignalingService` (WebSocket)
   - Exposes `LivestreamState` via `stateStream`

2. **MediaService** (`lib/src/livestream/services/media_service.dart`)
   - Tightly coupled to LiveKit (`livekit_client` package)
   - Manages room connection, audio tracks, participants

3. **SignalingService** (`lib/src/livestream/services/signaling_service.dart`)
   - WebSocket-based real-time communication
   - Handles chat, reactions, hand raises, moderation events

4. **UI Screens in Production**
   - `LiveProgramHostView` and `LiveProgramAudienceView` exist in `lib/src/features/go_live/presentation/screens/`
   - Currently display **mock/static data** (e.g., `getCoHostList()`, hardcoded comments)
   - **NOT connected** to `LivestreamController` or any real-time state

### The Gap
The livestream infrastructure exists but is **not wired to the UI**. The screens are shells that show mock data while the real-time services sit unused.

### HOWEVER - A Reference Implementation Exists!
There's a file called `lib/example_stream.dart` (1149 lines) that shows the **ideal integration**:

**How UI Interacts with LiveKit and WebSocket (via LivestreamController):**

1. **Initialization**:
   ```dart
   _controller = LivestreamController(streamId: widget.streamId, isHost: widget.isHost);
   await _controller.join();
   ```

2. **Media Service Interaction**:
   ```dart
   _controller.mediaService.toggleMicrophone(false/true)  // Mic control
   _controller.mediaService.localParticipant?.identity     // Get local participant
   _controller.mediaService.isAudioEnabled                  // Check if audio is on
   ```

3. **State Stream** (main UI data source):
   ```dart
   StreamBuilder<LivestreamState>(
     stream: _controller.stateStream,
     builder: (context, snapshot) {
       final state = snapshot.requireData;
       // Access: state.status, state.participants, state.messages, 
       //         state.reactions, state.handQueue, state.viewerCount
     },
   )
   ```

4. **Actions**:
   ```dart
   _controller.sendChat(msg)           // Chat via signaling
   _controller.raiseHand()              // Hand raise
   _controller.lowerHand()             // Lower hand
   _controller.toggleMute()            // Mute toggle
   _controller.sendReaction(emoji)     // Reactions
   _controller.startStream(contentId) // Host: start stream
   _controller.endStream()            // Host: end stream
   _controller.approveHandRaise(id)   // Host: approve hand raise
   ```

5. **Media Events Stream**:
   ```dart
   StreamBuilder<MediaStateChange>(
     stream: _controller.mediaService.onMediaStateChanged,
   )
   ```

This file demonstrates the full integration pattern that should be applied to the production screens.

## Refactoring Goal

Make the livestream provider-agnostic so we can:
1. Switch between LiveKit and Agora without changing UI code
2. Have clean separation of concerns
3. Properly connect the UI to the controller

---

## Implementation Plan

### Phase 1: Abstract the Media Layer

**Create `IMediaProvider` interface** in `lib/src/livestream/services/`

```
lib/src/livestream/services/
  ├── media_provider.dart          # NEW - Abstract interface
  ├── livekit_media_provider.dart  # NEW - LiveKit implementation (renamed from media_service.dart)
  └── agora_media_provider.dart    # NEW - Agora implementation (future)
```

**Interface methods:**
```dart
abstract class IMediaProvider {
  Future<void> connect({required String url, required String token, bool isSpeaker});
  Future<void> disconnect();
  Future<void> toggleMute();
  Future<void> setupAndPublishAudio();
  
  Stream<RemoteAudioTrack> get onRemoteAudioTrack;
  Stream<RemoteParticipant> get onParticipantJoined;
  Stream<RemoteParticipant> get onParticipantLeft;
  Stream<List<Participant>> get onActiveSpeakers;
  Stream<MediaStateChange> get onMediaStateChanged;
  
  bool get isConnected;
  LocalParticipant? get localParticipant;
  bool get isAudioEnabled;
}
```

**Update LivestreamController:**
- Change `MediaService _media` to `IMediaProvider _media`
- Inject different implementations via constructor

### Phase 2: Abstract the Signaling Layer

**Create `ISignalingProvider` interface** in `lib/src/livestream/services/`

```
lib/src/livestream/services/
  ├── signaling_provider.dart      # NEW - Abstract interface
  ├── websocket_signaling_provider.dart  # NEW - WebSocket implementation (refactored from signaling_service.dart)
```

**Interface methods:**
```dart
abstract class ISignalingProvider {
  Future<void> connect();

  Stream<SignalingEvent> get events;

  void sendReaction(String emoji);
  void raiseHand();
  void lowerHand();

```

**Update LivestreamController:**
- Change `SignalingService? _signaling` to `ISignalingProvider? _signaling`

## Key Design Decisions

1. **Constructor Injection**: Use DI to inject provider implementations into controller
2. **Keep Existing Models**: Extend rather than replace current models
3. **Minimal UI Changes**: Only update screens to use state, don't redesign
4. **Future-Proof Signaling**: Even though WebSocket may work for both providers, abstracting allows for alternative implementations

---
